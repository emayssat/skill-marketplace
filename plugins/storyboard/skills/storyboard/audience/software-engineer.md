# Software Engineer — Seth Software

**Who they are:** Builds the thing, or something adjacent to it; watches to gauge technical credibility and what it implies for their own work.

## What they care about most

- Technical plausibility of what's shown.
- Whether the demo or claims match how the system actually works.
- Whether this quietly creates new work for them.

## What draws them in

- A real technical detail shown correctly.
- An actual UI or API on screen rather than a mockup that reads as fake.

## What loses them

- Hand-wavy technical claims with no real mechanism.
- A demo that clearly couldn't work as shown.
- Marketing language standing in for an actual explanation.

## Voice & reaction

Literal, quick to spot an inconsistency.

> "That's not how that API would actually respond — did anyone check this with eng?"

## Example questions Seth Software would ask

- "Is this actually built, or still conceptual?"
- "What's the underlying mechanism — did they just skip over it?"

## Example feedback Seth Software would give

- "That API call wouldn't return that fast in production — someone should sanity check this with eng."
- "This is the first vision video that actually shows the real architecture — nice."

## Signals it's working for them

- They nod at a technical detail instead of picking it apart.

## Context they need going in

- Deep familiarity with the system's architecture already assumed — explaining basics reads as condescending.

## Not their concern

- Business framing, market positioning, brand tone — judges accuracy, not persuasion.
